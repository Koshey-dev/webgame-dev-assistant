# Архитектура

## Кто за что отвечает

- **GitHub** — источник истины: код, карточки `knowledge/`, реестр `sources.toml`,
  контрольный набор. Карточки правит только автор проекта.
- **Сервер** (VPS, позже Mac mini в домашней сети) — релиз: git-тег из GitHub,
  выкатывается вручную. Сервер сам собирает официальные страницы в `data/`,
  строит индекс и отвечает в чате. Карточки он не меняет.

## Ход вопроса о требованиях

1. **Запрос к базе.** Модель переписывает вопрос в поисковый запрос с учётом
   истории: «а на Яндексе?» после вопроса про размер билда превращается в
   «лимит размера билда Яндекс Игры / Yandex Games build size limit». Английский
   хвост нужен, потому что половина источников англоязычная.
2. **Площадки.** Если в вопросе или запросе названы площадки (`rag.mentioned`),
   поиск идёт только по ним, по равной доле на каждую.
3. **Поиск.** Косинус эмбеддингов embeddinggemma по трём видам кусков: карточки,
   куски страниц, заметки «Мой опыт». Топ-10.
4. **Отбор.** Кусок идёт в ответ, если он выше порога `RAG_THRESHOLD` (0,54) и не
   уступает лучшему куску своей площадки больше чем на 0,1. Не больше 6 кусков и
   ограничение по символам: у локальной модели 2600, у облачной 4500.
5. **Ниже порога** ответ пишет код: «в базе требований этого нет» и ближайшие разделы.
   Порог подобран контрольным набором `eval/questions.toml` (`py scripts/eval.py deepseek`):
   худший вопрос по базе дал лучший косинус 0,589, лучший вопрос вне базы — 0,504;
   0,54 — середина окна. Сменится эмбеддер или база — порог подбирать заново.
6. **Ответ.** Модель получает вопрос, а под ним пронумерованные фрагменты:
   вопрос перед фрагментами понимается лучше. Номера [n] в тексте ссылаются
   на источники.
7. **Источники** собирает код: площадка, раздел, вид (карточка, страница, мой
   опыт), дата сверки, цитата. Если страница менялась после даты сверки
   карточки, источник помечается «требует сверки».

## Ход `/help`

1. MCP-клиент знакомится с сервером git (`initialize`, `tools/list`).
2. Код вызывает `git_branch` всегда: ветка (на сервере — тег релиза) и последний коммит.
3. Поиск по базе «Проект»: README и `docs/`.
4. Модель получает вопрос, данные git и фрагменты, а также инструменты
   `git_status`, `git_log`, `list_files`. До трёх кругов вызовов, каждый вызов
   виден в чате карточкой MCP.

## Данные

Одна база SQLite `data/assistant.db`: страницы (`pages`), индекс (`chunks`),
кеш эмбеддингов (`cache`), чаты (`chats`). Схема — в `docs/data.md`.

Индекс пересобирается одной транзакцией: прерванная сборка старый индекс не
портит. Кеш эмбеддингов идёт по хешу входа, поэтому правка одной страницы
пересчитывает только её куски.

## Почему так

- **Резка по разделам**, а не окнами фиксированного размера: на стенде курса
  (день 21) окна рвали фразы в 80% кусков, разделы — в 0%.
- **Порог плюс переписанный запрос** вместо реранкера: реранкер дороже в 2,5
  раза, а для медленной локальной модели каждый лишний вызов — секунды.
- **Решения кодом, а не просьбой в промпте**: «в базе нет», источники и цитаты
  не зависят от того, послушалась ли модель.
- **Хеш текста страницы** вместо `lastmod` и ETag: у части площадок `lastmod` —
  дата деплоя всего сайта, у Яндекса ETag нет совсем.
- **Мало инструментов MCP**: каждый инструмент — описание в каждом запросе к модели.
