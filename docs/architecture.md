# Архитектура

## Кто за что отвечает

- **GitHub** — источник истины: код, карточки `knowledge/`, реестр `sources.toml`,
  контрольный набор. Карточки правит только автор проекта.
- **Сервер** (VPS, позже Mac mini в домашней сети) — релиз: git-тег из GitHub,
  выкатывается вручную. Сервер сам собирает официальные страницы в `data/`,
  строит индекс, отвечает в чате и делает ревью PR. Карточки он не меняет.
- **GitHub Actions** — только транспорт ревью: diff PR уходит на сервер, ответ
  приходит комментарием в PR. Ключа модели в GitHub нет.

## Ход вопроса о требованиях

1. **Запрос к базе.** Модель переписывает вопрос в поисковый запрос с учётом
   истории: «а на Яндексе?» после вопроса про размер билда превращается в
   «лимит размера билда Яндекс Игры / Yandex Games build size limit». Английский
   хвост нужен, потому что половина источников англоязычная.
2. **Площадки.** Если в вопросе или запросе названы площадки (`rag.mentioned`),
   поиск идёт только по ним, по равной доле на каждую.
3. **Поиск.** Косинус эмбеддингов embeddinggemma по трём видам кусков: карточки,
   куски страниц, заметки «Мой опыт». Топ-10.
4. **Отбор.** Кусок идёт в ответ, если он выше порога `RAG_THRESHOLD` (0,54) и не
   уступает лучшему куску своей площадки больше чем на 0,1. Не больше 6 кусков и
   ограничение по символам: у локальной модели 2600, у облачной 4500.
5. **Ниже порога** ответ пишет код: «в базе требований этого нет» и ближайшие разделы.
   Порог подобран контрольным набором `eval/questions.toml` (`py scripts/eval.py deepseek`):
   худший вопрос по базе дал лучший косинус 0,589, лучший вопрос вне базы — 0,504;
   0,54 — середина окна. Сменится эмбеддер или база — порог подбирать заново.
6. **Ответ.** Модель получает вопрос, а под ним пронумерованные фрагменты:
   вопрос перед фрагментами понимается лучше. Номера [n] в тексте ссылаются
   на источники.
7. **Источники** собирает код: площадка, раздел, вид (карточка, страница, мой
   опыт), дата сверки, цитата. Если страница менялась после даты сверки
   карточки, источник помечается «требует сверки».

## Ход `/help`

1. MCP-клиент знакомится с сервером git (`initialize`, `tools/list`).
2. Код вызывает `git_branch` всегда: ветка (на сервере — тег релиза) и последний коммит.
3. Поиск по базе «Проект»: README и `docs/`.
4. Модель получает вопрос, данные git и фрагменты, а также инструменты
   `git_status`, `git_log`, `list_files`. До трёх кругов вызовов, каждый вызов
   виден в чате карточкой MCP.

## Ход ревью PR

1. **Action** (`.github/workflows/review.yml`) на PR из своего репозитория: diff
   от точки ветвления и полные тексты изменённых файлов → `POST /api/review` с
   Bearer-токеном `REVIEW_TOKEN`. PR из форка секретов не получает и не ревьюится.
2. **Карточки** `knowledge/` из PR сверяет код (`cards.problems`) со страницами
   сервера: цитата не нашлась, нет источника, дата сверки в будущем. Модель их
   не читает.
3. **Контекст.** Этот документ — правила проекта — идёт целиком всегда: поиск
   правило к коду правки не подбирает (косинус 0,26). README, `docs/` и база
   «Код» (функции и классы, `app/codecut.py`) — по RAG, запрос на каждый файл;
   куски самих изменённых файлов не берутся: в индексе их версия релиза, и
   модель находила «расхождения» старого кода с diff. Полный текст получает
   код, от меньших файлов к большим, пока помещается.
4. **Модель** — всегда DeepSeek, не модель чата: локальная 1.5B на одном ядре
   VPS для ревью слаба и не укладывается во время. Получает diff с номерами строк
   нового файла и отвечает JSON: баги, архитектура, рекомендации — с файлом,
   строкой и номерами фрагментов. База «Код» — исходники самого ассистента
   (корень проекта), а не репозиторий `WDA_REPO`, который видит MCP git.
5. **Код проверяет ответ**: замечание на файл вне PR отбрасывается, строка вне
   файла убирается, `@упоминания` и HTML-комментарии обезврежены — текст PR
   мог подсказать их модели. Комментарий собирает код, Action обновляет один и
   тот же комментарий на каждый пуш.

## Ход тикета поддержки

Игрок жмёт в игре «Сообщить об ошибке», игра шлёт баг-репорт (формат —
`docs/bug-report.md`), в CRM он становится тикетом. Разработчик открывает тикет
во вкладке «Тикеты» или командой `/ticket <id> [вопрос]`; уточнения в том же
чате идут по тому же тикету.

1. **CRM через MCP.** Тикет, игрока и его другие тикеты код берёт у MCP-сервера
   CRM (`/mcp/support`: `ticket_list`, `ticket_get`, `player_get`) — всегда сам.
   Модель инструментов не получает: просьбе «покажи данные игрока p-0001» в
   тексте игрока нечем выполниться.
2. **Всё из игры — недоверенные данные**, не только комментарий: баг-репорт
   собирает клиент. Строки режутся по длине, управляющие символы и разделители
   `<<<` `>>>` убираются, похожее на инъекцию помечается — пометка видна в
   чате и уходит модели.
3. **Расхождения — кодом.** «Я вошёл» при `state.auth = false`, «купил» без
   оплаченной покупки в CRM — код находит сам, модель добавляет свои.
4. **Поиск** по FAQ игры и общему FAQ (`support/faq/`) со своим порогом
   `FAQ_THRESHOLD` и по базе площадки тикета — как в чате.
5. **Модель** отвечает JSON: разбор для разработчика с [n], расхождения, шаги,
   чего не хватает, черновик ответа игроку на языке тикета.
6. **Черновик проверяет код**: ссылки, которых нет в найденных фрагментах,
   вырезаются; внутренние детали (id игроков, поля, файлы) и обещания
   компенсаций помечаются предупреждением.

## Данные

Одна база SQLite `data/assistant.db`: страницы (`pages`), индекс (`chunks`:
площадки, «Мой опыт», «Проект», «Код», «Поддержка» — FAQ игр),
кеш эмбеддингов (`cache`), чаты (`chats`). Схема — в `docs/data.md`.

Индекс пересобирается одной транзакцией: прерванная сборка старый индекс не
портит. Кеш эмбеддингов идёт по хешу входа, поэтому правка одной страницы
пересчитывает только её куски.

## Почему так

- **Резка по разделам**, а не окнами фиксированного размера: на стенде курса
  (день 21) окна рвали фразы в 80% кусков, разделы — в 0%.
- **Порог плюс переписанный запрос** вместо реранкера: реранкер дороже в 2,5
  раза, а для медленной локальной модели каждый лишний вызов — секунды.
- **Решения кодом, а не просьбой в промпте**: «в базе нет», источники и цитаты
  не зависят от того, послушалась ли модель.
- **Хеш текста страницы** вместо `lastmod` и ETag: у части площадок `lastmod` —
  дата деплоя всего сайта, у Яндекса ETag нет совсем.
- **Мало инструментов MCP**: каждый инструмент — описание в каждом запросе к модели.
- **Ревью на сервере, а не в раннере**: ключ модели не уходит в секреты GitHub,
  эмбеддер и индекс уже есть на сервере, раннеру нужен только `python3` без pip.
- **Ответ ревью — JSON, комментарий собирает код**: только так можно проверить,
  что замечание про файл из PR, а не выдумано.
